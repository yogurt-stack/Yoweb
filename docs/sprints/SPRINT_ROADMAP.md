# Yoweb Sprint 实施路线图

## 1. 文档目的

本文件把 `PROJECT_PLAN.md` 中已经确认的 D0～D17，转换为可分阶段执行的开发路线。

它回答以下问题：

- 每个 Sprint 要解决什么问题？
- 本阶段应该实现什么，不应该实现什么？
- 哪些需求完成后才能进入下一阶段？
- Codex 或开发人员需要提交哪些验证证据？

本文件不替代 `PROJECT_PLAN.md`。发生冲突时，以 `PROJECT_PLAN.md` 中的数据语义、来源证据和产品边界为准。

## 2. Sprint 使用方式

- Sprint 表示一个可验收的能力增量，不强制对应固定自然周。
- 每次只实施一个 Sprint。
- 当前 Sprint 未验收前，不提前展开后续 Sprint。
- 每个 Sprint 开始前，再补充一份更细的 `SPRINT-XX-SPEC.md`。
- 实现过程中如果需要改变 D0～D17，必须暂停并由用户确认。
- 不以“页面能打开”作为完成标准，必须验证数据语义和失败路径。

## 3. 总体顺序

```text
Sprint 1  Question 核心题库
    ↓
Sprint 2  来源、证据与收录 Inbox
    ↓
Sprint 3  精选 GitHub 自动导入
    ↓
Sprint 4  LLM 提取与整理 Workflow
    ↓
Sprint 5  去重、关系与可恢复合并
    ↓
Sprint 6  混合检索与检索评估
    ↓
Sprint 7  个人训练 Workflow
    ↓
Sprint 8  调度、备份、恢复与整体加固
```

## 4. 阶段总览

| Sprint | 核心目标 | 阶段性成果 | 进入下一阶段的关键门槛 |
|---|---|---|---|
| 1 | 建立 Question-first 题库 | 可以创建、编辑、整理和查找自建题目 | 无来源题目可以完整保存和恢复 |
| 2 | 建立来源证据和审核入口 | URL/摘录进入 Inbox，审核后入库 | 自动候选不会直接污染正式题库 |
| 3 | 接入第一个自动化来源 | 白名单 GitHub 仓库可重复、幂等导入 | 重复运行不重复计数，License 可追溯 |
| 4 | 接入生成式 LLM | 提取、归一化、分类和难度建议 | 结构校验失败不会写正式题库 |
| 5 | 建立高质量去重 | 候选发现、LLM Judge、用户确认、可恢复合并 | 原始证据和训练历史不会丢失 |
| 6 | 建立混合检索 | 关键词、别名、向量、排名融合和评估集 | 基础召回有效，LLM 失败可降级 |
| 7 | 建立个人训练闭环 | 选题、回答、评价、追问和历史 | 状态可恢复，训练数据不污染来源统计 |
| 8 | 支持长期本地运行 | 定时任务、预算、备份、恢复、导出 | 完整 MVP 端到端验收通过 |

## 5. Sprint 1：Question 核心题库

### 5.1 阶段目标

完成最小但正确的 Question-first 垂直闭环。用户不需要先找到面经、公司或岗位，就能把一道题放入题库并进行基础整理。

### 5.2 范围

- 建立 Next.js、React、TypeScript 项目骨架。
- 建立 Node.js 应用服务层和后台 Worker 入口骨架。
- 建立 SQLite、Drizzle 和数据库迁移机制。
- 实现 Question、Original Wording、Topic、Tag 的基础领域模型。
- 实现 Question 快速创建、列表、详情、编辑、归档和恢复。
- 实现 `INBOX` 与 `ORGANIZED` 两种整理状态。
- 实现作答任务类型和题库参考难度。
- 实现基础关键词包含查询和明确筛选。
- 实现基础数据导出或最小手动备份入口。
- 建立项目运行、迁移和测试说明。

### 5.3 本阶段页面

- 题库首页/列表页
- 快速添加 Question 页面或弹窗
- Question 详情页
- Question 编辑页
- Topic/Tag 基础管理入口

### 5.4 本阶段不做

- 来源材料和面经导入
- GitHub API
- LLM
- Embedding
- 语义检索
- 去重合并
- 训练评价
- 定时任务
- 云部署和多用户

### 5.5 交付物

- 可本机启动的 Web 应用
- 初始数据库迁移
- Question 领域服务
- 基础页面和 API
- 领域单元测试
- 最小端到端测试
- README 中的本机启动说明

### 5.6 验收标准

1. 能创建一条没有任何来源信息的 Question。
2. 能编辑标准题目、作答任务、Topic、Tag、难度和整理状态。
3. 能为 Question 增加多个 Original Wording。
4. Original Wording 不会因为编辑标准 Question 而改变。
5. 应用重启后数据仍存在。
6. Question 归档后默认不出现在正常列表，恢复后重新出现。
7. 关键词和明确筛选在没有 LLM 的情况下工作。
8. 迁移、测试和构建命令执行成功。

### 5.7 阶段演示

```text
新建“如何设计 Coding Agent 的工具重试机制？”
→ 不填写来源
→ 添加 Agent / Coding Agent 领域
→ 添加 Tool Calling 标签
→ 标记为已整理
→ 通过关键词重新找到该题
```

### 5.8 建议代码规模

业务和测试代码合计约 4,000～8,000 行，仅作为范围检查依据，不作为质量指标。

## 6. Sprint 2：来源、证据与收录 Inbox

### 6.1 阶段目标

建立“来源材料可以进入系统，但不会直接污染正式题库”的审核闭环。

### 6.2 范围

- 实现 Source、Raw Document、Raw Document Version、Evidence。
- 实现 Question Mention。
- 实现 Company、Job、Interview 和 Interview Occurrence 的最小结构。
- 实现手动 URL、标题、合法摘录和个人笔记录入。
- 实现来源保存权限和外部模型发送权限标记。
- 实现 Import Batch、Import Item 和 Inbox。
- 实现批量接受、忽略和修改后接受。
- 实现内容指纹和重复导入检测。
- 实现资料收录次数与面试报告次数的独立展示。

### 6.3 本阶段页面

- 手动收录材料页面
- Source/Raw Document 详情页
- Import Inbox 页面
- 批量审核界面
- Question 证据与上下文区域

### 6.4 本阶段不做

- GitHub 自动导入
- 牛客批量抓取
- LLM 自动提取
- Embedding 和语义检索
- 自动去重
- 自动创建 Interview Occurrence

### 6.5 交付物

- 来源与证据领域模型
- 手动导入流程
- Inbox 审核流程
- Mention 和 Occurrence 独立统计
- 重复材料检测测试
- 证据边界测试

### 6.6 验收标准

1. 用户可以只保存 URL、标题和个人笔记，不强制保存全文。
2. 同一 Raw Document 重复导入不会产生重复 Mention。
3. 一个候选题只有在用户接受后才进入正式题库。
4. GitHub 资料中的题目只产生资料 Mention，不自动产生 Interview Occurrence。
5. JD 中的技术要求不自动成为真实面试题。
6. 用户可以为真实面经手动建立 Interview 和 Occurrence。
7. Question 详情页分别显示资料出现次数和面试报告次数。
8. 页面失效后可以保留已有合法证据和失效状态。

### 6.7 阶段演示

```text
手动粘贴一段合法面经摘录
→ 创建 Import Batch
→ 显示候选题和证据
→ 用户选择其中两题加入题库
→ 一题关联 Interview Occurrence
→ 另一题仅作为资料 Mention
```

## 7. Sprint 3：精选 GitHub 自动导入

### 7.1 阶段目标

接入第一个低风险、可控、可重复运行的自动化来源，验证采集适配器和后台任务边界。

### 7.2 开始前需要用户提供

- 第一个测试仓库 URL
- 是否只处理指定文件或目录
- 仓库 License 判断结果
- 允许保存的内容范围
- 预计更新频率

### 7.3 范围

- 实现 GitHub 仓库白名单。
- 优先通过官方 API 获取仓库、文件和提交元数据。
- 保存仓库、路径、提交版本、License 和原始链接。
- 实现文件和提交变化检测。
- 实现 API 限流、超时、部分成功和可重试失败。
- 自动导入结果进入 Inbox。
- 建立来源适配器统一返回契约。
- 建立测试夹具，避免测试完全依赖实时 GitHub 网络。

### 7.4 本阶段不做

- GitHub 全站搜索和批量发现
- 未经白名单确认的仓库导入
- 自动复制许可不明确的内容
- 牛客和其他社区自动化
- 浏览器自动化
- LLM 自动提取

### 7.5 交付物

- GitHub Source Adapter
- 白名单管理入口
- GitHub 导入任务
- 变化检测和幂等保护
- 限流与错误状态展示
- 一个真实测试仓库的验收记录

### 7.6 验收标准

1. 非白名单仓库不能被后台自动处理。
2. 导入记录包含仓库、文件路径、提交版本、License 和 URL。
3. 相同提交重复执行不会重复创建 Raw Document Version。
4. 新提交有实质变化时生成新版本或更新建议。
5. 自动获取结果只进入 Inbox。
6. API 限流或网络错误不会破坏已有题库。
7. 单文件失败时其他文件仍可成功处理。

### 7.7 阶段演示

```text
将一个许可明确的仓库加入白名单
→ 手动触发首次导入
→ 生成 Inbox 候选
→ 再次执行不产生重复数据
→ 仓库更新后只生成变化建议
```

## 8. Sprint 4：LLM 提取与整理 Workflow

### 8.1 阶段目标

让 LLM 承担语言理解工作，但不能直接掌控状态和正式题库写入。

### 8.2 开始前需要用户提供

- 模型 API Key 和预算配置
- 约 10～20 份固定评测材料
- 期望的人工修订标准
- 可发送给外部模型的内容范围

### 8.3 范围

- 建立生成式 LLM Provider 接口。
- 接入一个通过评测的默认模型。
- 实现 Prompt 版本管理。
- 实现运行时 JSON Schema 校验。
- 实现非结构化材料的题目提取。
- 实现标准题目归一化建议。
- 实现 Topic、Tag 和难度建议。
- 显示模型建议、置信度和原始证据。
- 记录模型、版本、用途、Token 和成本。
- 所有结果进入 Inbox。

### 8.4 本阶段不做

- LLM 直接写正式题库
- LLM 自主访问整个 SQLite
- LLM 自主浏览互联网
- 多模型自动路由
- 自动合并重复题
- 训练评价

### 8.5 交付物

- LLM Provider Adapter
- 提取、归一化、分类、难度建议 Workflow
- Prompt 和输出契约
- 固定样本评测报告
- 调用日志与预算统计
- 模型不可用时的人工降级流程

### 8.6 验收标准

1. 模型只接收当前任务必要材料。
2. 模型输出不符合 Schema 时不会进入正式题库。
3. 模型提取的每道题都能定位到原始证据。
4. 模型扩展要求不会被标记为真实原题。
5. 分类建议和正式分类分开显示。
6. Prompt 和模型版本可追溯。
7. 达到预算限制时后台模型任务停止，手动题库仍可用。
8. 固定样本的忠实性和人工修订量达到用户可接受水平。

## 9. Sprint 5：去重、关系与可恢复合并

### 9.1 阶段目标

建立高质量题目去重流程，避免只依靠字符串或向量分数进行错误合并。

### 9.2 开始前需要用户提供

- 一组同题、相关题、不同题和不确定题样本
- 对宽泛题和具体题粒度的人工判断案例

### 9.3 范围

- 实现字符串标准化和精确重复检查。
- 实现受控别名候选。
- 建立 Embedding Provider 接口。
- 为 Question 和确认关联的 Original Wording 生成向量。
- 向量保存在 SQLite，由 Node.js 本地计算相似度。
- 实现疑似重复候选列表。
- 实现 LLM Judge 结构化关系判断。
- 实现用户确认 SAME、RELATED、DIFFERENT、UNCERTAIN。
- 实现已确认关系持久化。
- 实现可恢复合并及撤销合并。

### 9.4 本阶段不做

- 相似度超过固定值自动合并
- LLM 判断后静默合并
- 每次查询都重新判断已确认关系
- Qdrant 或独立向量数据库
- 大规模近似向量索引

### 9.5 交付物

- Embedding Adapter
- 本地向量存储和相似度计算
- 去重候选页面
- LLM Judge Workflow
- 关系确认和合并历史
- 撤销合并能力
- 去重测试集报告

### 9.6 验收标准

1. Embedding 只产生候选，不能自动证明同题。
2. LLM 必须按考查目标、作答任务和关键约束判断。
3. 用户确认后关系才成为正式关系。
4. 已确认关系查询时由数据库稳定返回。
5. 合并后 Original Wording、Evidence、Mention 和训练历史不丢失。
6. 撤销合并可以恢复合并前的题目结构。
7. 不确定题可以长期保持 UNCERTAIN，而不被强制处理。

## 10. Sprint 6：混合检索与评估

### 10.1 阶段目标

让用户能够通过关键词、筛选条件和自然语言找到相关题目，同时保证统计和证据口径正确。

### 10.2 开始前需要用户提供

- 约 30～50 条真实查询
- 每条查询应该找到的题目或结果范围
- 完全无关查询样本

### 10.3 范围

- 完善关键词和受控别名检索。
- 实现公司、岗位、时间、领域、标签、难度和状态筛选。
- 实现 Embedding 语义召回。
- 实现排名融合。
- 实现精确标题和别名的确定性优先。
- 复杂歧义查询支持少量候选 LLM 重排。
- 实现本地排序降级。
- 展示命中依据。
- 建立检索评估集和可重复评估命令。

### 10.4 本阶段不做

- Elasticsearch/OpenSearch
- 独立向量数据库
- LLM 读取整个题库
- 每次查询都调用 LLM
- 用语义相关性推断真实面试证据
- 复杂推荐模型

### 10.5 交付物

- 混合检索服务
- 检索页面
- 排名融合配置
- 可选 LLM 重排
- 命中依据展示
- 评估集和评估报告

### 10.6 验收标准

1. 精确标题和受控别名优先返回。
2. 同义改写能通过语义检索找到目标题目。
3. 完全无关查询不会被强行标记为高相关。
4. LLM 不可用时仍返回本地检索结果。
5. 公司、岗位、时间严格查询只统计有证据的记录。
6. 资料收录次数和面试报告次数独立显示。
7. 调整 Embedding 模型、阈值或融合参数后可以重跑同一评估集。

### 10.7 阶段演示

```text
查询“Agent 工具调用失败后如何恢复”
→ 严格筛选目标领域
→ 关键词和向量分别召回
→ 排名融合
→ 返回重试、幂等、降级和停止条件相关题
→ 显示每题的命中依据和已确认关系
```

## 11. Sprint 7：个人训练 Workflow

### 11.1 阶段目标

建立从选题、回答、评价、追问到训练历史的个人训练闭环。

### 11.2 开始前需要用户确认

- 首版评价维度
- 单次训练题目数量默认值
- 最大追问轮数
- 用户自评方式

### 11.3 范围

- 实现 Training Session、Attempt、Assessment、Follow-up。
- 实现训练状态机。
- 支持按岗位、领域、难度和题量开始训练。
- 程序根据规则选题。
- 用户提交回答和自评。
- LLM 按固定评价结构分析回答。
- 程序决定是否进入有限追问。
- 保存训练历史和简单薄弱点汇总。
- 支持中断后恢复当前训练会话。

### 11.4 本阶段不做

- 自主训练 Agent
- 多轮无限追问
- 复杂心理测评或能力模型
- 自动修改 Question 难度
- 自动把追问加入真实题库
- 语音和实时视频面试

### 11.5 交付物

- 训练创建和答题页面
- 训练状态机
- 选题服务
- LLM 评价 Workflow
- 追问流程
- 训练历史页面
- 训练数据隔离测试

### 11.6 验收标准

1. 能按岗位或领域创建训练会话。
2. 程序而不是 LLM 选择和提交下一道 Question。
3. 每次回答和评价独立保存，不覆盖历史。
4. 评价包含具体覆盖点、错误和改进建议。
5. 追问有最大轮数并关联当前回答。
6. 中断后能够恢复会话状态。
7. 训练生成内容不增加资料或面试频率。
8. 可以查看某个 Question 的历史训练记录。

---

## 12. Sprint 8：调度、备份、恢复与整体加固

### 12.1 阶段目标

让系统能够在个人电脑上长期、稳定、可恢复地运行，并完成完整 MVP 验收。

### 12.2 范围

- 实现基于 SQLite 持久化规则的任务调度。
- Web 进程和 Worker 进程分开运行。
- 实现手动触发和按来源定期更新。
- 实现任务部分成功、有限重试和范围重跑。
- 实现模型预算提醒与后台硬限额。
- 实现自动版本化备份和手动备份。
- 实现非破坏性的恢复验证。
- 实现 Question、Evidence、Relation、Training 的数据导出。
- 完善本机访问限制和密钥管理。
- 完成完整端到端验收。

### 12.3 本阶段不做

- 云端高可用部署
- 公网访问
- 多用户认证和权限系统
- Redis/Celery/Temporal
- Kubernetes
- 异地备份自动同步

### 12.4 交付物

- Worker 运行入口
- 持久化调度和任务状态页面
- 重试、预算和失败处理
- 自动/手动备份
- 恢复验证报告
- 数据导出
- 完整部署和运行手册
- MVP 端到端测试报告

### 12.5 验收标准

1. 浏览器关闭后后台任务仍可由 Worker 执行。
2. 电脑休眠或关机不会造成任务重复写入；恢复后可继续检查。
3. 单个来源失败不影响其他来源和已有题库。
4. 达到模型预算上限后后台调用暂停。
5. 自动备份和手动备份均可生成版本。
6. 恢复验证能证明核心实体数量和关联一致。
7. 导出的数据可以脱离当前 UI 阅读或迁移。
8. 完整 MVP 验收场景通过。

## 13. 完整 MVP 验收路径

```text

→ 运行备份并验证恢复
```

## 14. 每个 Sprint 的 Definition of Done

一个 Sprint 只有同时满足以下条件才算完成：

1. 范围内的功能需求已实现。
2. 明确列出的非目标没有被偷偷带入。
3. 核心领域规则有自动化测试。
4. 数据库迁移可以从空库执行。
5. 失败和边界场景有验证记录。
6. 构建、类型检查和测试通过。
7. 本机手动演示路径通过。
8. README 或 Sprint 文档已更新。
9. 没有把密钥、Cookie 或个人敏感信息提交到 Git。
10. 开发人员提交修改文件、实现需求、测试结果、假设和遗留问题报告。
